# Private local data bootstrap

The first Phase 2 step is a private, versioned source generation for local
snapshot building. It is not part of the public website, and raw game data
must not be committed to Git or placed under the static web root.

## Why this is the first step

The current daily job rebuilds many BigQuery derivatives and then submits a
separate query for each default page/view. Filters can submit additional
queries. The static JSON files are not the main cost problem; the repeated
BigQuery analysis is.

The bootstrap exports the canonical Full Sample once and the physical Logs
table once into a private, versioned Cloud Storage generation. A later local
builder will read these Parquet files, reproduce the prepared observation
contracts, and generate the same snapshots with local CPU/disk instead of
BigQuery analysis. One coherent generation also makes parity and rollback
checks possible.

## Commands

Use the bundled Python runtime or a private worker environment with
`google-cloud-bigquery` and `google-cloud-storage` installed.

```text
python analysis/phase2-local-import.py plan
```

`plan` reads only BigQuery metadata. It reports the source schema, physical
Logs size, and a stable source fingerprint. It does not run a game-data
query.

Before an explicit export, configure a private bucket and prefix:

```text
$env:PHASE2_IMPORT_BUCKET = "<private-import-bucket>"
$env:PHASE2_IMPORT_PREFIX = "phase2/source"
python analysis/phase2-local-import.py export
```

`export` performs exactly one `EXPORT DATA AS SELECT` for the canonical Full
Sample and one native Parquet extract for Logs. It records the BigQuery job ID
and bytes processed in a manifest. The generation is never promoted to a
serving pointer by this tool.

```text
python analysis/phase2-local-import.py download <generation> C:\private\ark-nova\source
```

Download is intended for the private builder/benchmark machine. The data must
remain outside the public repository and static hosting directory.

After download, build the first local read-only generation:

```text
python analysis/phase2-local-build.py \
  C:\private\ark-nova\source\phase2-20260915-b57235ad65db \
  C:\private\ark-nova\generations\phase2-20260915-b57235ad65db.duckdb
```

The builder stores the two canonical source relations in DuckDB and writes a
small adjacent manifest with row counts, distinct tables, columns, and local
build time. It is intentionally not yet a public serving switch. The serving
prototype keeps reusable player-game and card-play facts local, while computing
pair and CI relations as focused, indexed reads. A naïve all-card-pairs table
was deliberately not retained: building every possible pair caused unnecessary
local expansion and was stopped before it completed.

The first generation has now been built locally as
`phase2-20260915-b57235ad65db.duckdb`. It contains 5,531,256 Full Sample rows
and 436,526 Logs rows, materialized in 146.894 seconds. The resulting DuckDB
file is about 848 MB. A representative local MW card-play aggregation counted
3,217,002 nested play observations in 6.745 seconds and grouped them into 160
cards in 7.273 seconds. These are local CPU/disk measurements, not BigQuery
usage, and are a baseline rather than a production performance guarantee.

The first narrow serving slice has also been materialized locally. It contains
5,531,256 player-game rows and 7,797,585 deduplicated normal-card play rows
across 280 card/type groups. It also contains 431,641 joined player-log rows,
11,341,845 distinct in-hand facts, and 28,388,686 distinct seen facts. The
in-hand and seen relations are reusable compact facts: a raw-Logs set check
using the Cards query's exact player join found zero missing or extra rows.
Their numerical parity is checked at the
population-shape level against the current MW Cards snapshot. After applying
the Cards default scope (MW, valid maps, dates from 2025-01-01, both Elo
minimums 300, excluded projects, null deltas omitted, and the table-level
corruption predicate), the local slice contains the same 267 card groups as
the snapshot, 4,186,109 distinct table/card counts, and 4,271,252 non-null
delta observations. The full unrounded local means and the older rounded
snapshot values still differ, as expected while the published pack remains on
the previous successful version; this is not yet a same-version production
parity pass.

The focused report is
`analysis/phase2-local-reconcile-cards-mw.json`, generated by
`analysis/phase2-local-reconcile.py`. It records the snapshot version
`2026-09-14T01:16:09.085507+00:00`, the published marker version
`2026-09-15T20:07:14.508346+00:00`, and the private export generation created
at `2026-09-15T21:02:04Z`. The refresh failure preserved the older atomic pack;
the local export therefore cannot be judged against it as if both were the
same data version.

The local derivation found 8,988 distinct tables matching the corruption
predicate in the 2026-09-15 export, including 166 tables with MW valid-map
card plays (4,126 card-play rows). A direct current-source audit on 2026-09-16
found 9,021 tables: 5,295 MW and 3,726 Base. The current source has 5,419 more
two-player tables and only 33 more corrupted tables than the export, so source
growth is the leading explanation for the difference. The earlier 7,663 count
has no retained ID set and cannot be reconciled completely after the fact; no
production exclusion is rebuilt from a hard-coded count. Full diagnostics and
the ten inspection IDs are in `analysis/phase2-corrupted-current-audit.md`.

The current DuckDB file is approximately 1.84 GB after the rebuilt narrow
slice. The earlier 848 MB figure describes the source-only stage, before
materialized player-game, card-play, and flattened card-fact relations were
added. DuckDB may retain free pages from the interrupted exploratory pair
build, but no quadratic pair relation is present or used. Future work should
use focused pair reads or compact aggregate keys instead of materializing the
full quadratic pair space.

## Safety contract

- The default command is metadata-only and free of BigQuery analysis charges.
- Export is explicit and writes only to the caller-selected private bucket.
- Each generation has an immutable-looking directory and manifest; a partial
  generation cannot replace the previous one.
- Parquet is a storage/transfer format only. It does not round values or alter
  nulls, nested Logs arrays, player identity, map, completion, corruption,
  Arena, Tournament, or starting-position semantics.
- The canonical Full Sample export excludes only the unused `last_x_games`
  source field; Last X is calculated by the dashboard contract after the
  active eligibility filters.
- Logs are extracted natively so their nested event fields remain available
  to the local preparation step.
- No change is made to the deployed Cloud Function or refresh schedules by
  running `plan`, `export`, or `download`.

## Current prototype measurements

`analysis/phase2-local-benchmark-report.json` records read-only measurements on
the same DuckDB generation. Full Sample and Logs counts complete in under 0.15
seconds; filtered MW card-play shape takes 2.817 seconds; grouped MW card deltas
take 4.362 seconds; a filtered player history takes 0.358 seconds; a fixed
Card-and-Card Actual query takes 2.271 seconds; an ordinary table-clustered
card CI takes 0.975 seconds. The strict MW action-card eligibility scan takes 3.683
seconds. Four concurrent read-only readers complete in 0.218 seconds with
consistent results. These are local workstation baselines, not an e2-micro
capacity claim.

The same benchmark was then run on the private `e2-small` VM
`ark-nova-duckdb-test` in `europe-west1-c`. It completed in 37.18 seconds with
934,592 KiB (about 913 MiB) maximum resident memory, no swaps, and consistent
results across four concurrent readers. The VM report is
`analysis/phase2-vm-benchmark-report.json`. This confirms that the prototype is
feasible on the selected class of machine, but common public requests must use
compact precomputed aggregates rather than repeating the largest scans.

The local Cards snapshot producer is also implemented in
`analysis/phase2-local-cards-snapshot.py`. It reads the materialized in-hand
and seen facts, produces the complete 267-row Cards payload atomically in
29.776 seconds on the workstation, and its population reconciliation reports
zero card-group or `n_played` mismatches against the local query contract. The
pre-materialization run took 51.310 seconds, so this serving-side change cuts
the snapshot query time substantially. On the VM, the complete 3.80 GB database
was transferred and the read benchmark succeeded. The first Cards build on the
2-GiB machine was stopped after about eight minutes without output; after
resizing to `e2-medium` (4 GiB), the same build was killed by signal 9 after
21.47 seconds at 3,642,224 KiB maximum resident memory with no swap. Card +
Card was not started after this out-of-memory result. A larger VM or a compact
aggregate serving-build redesign is required for the remaining VM build test.

The local Card + Card producer is implemented in
`analysis/phase2-local-card-card-snapshot.py`. It produces the complete
13,456-row default payload with point estimates and retained standalone
component/Actual intervals in 28.591 seconds on the workstation after reading
the persisted default-scope pair-by-table relation. Bamboo Forest + Expert In
Herbivores has 1,191 observations, matching the private reference pair count.
Additive Synergy intervals are intentionally not calculated. The pair relation
contains 33,425,349 rows; the current producer keeps it temporary rather than
publishing a quadratic serving table.

`analysis/phase2-local-reconcile-card-card.json` adds a focused point-estimate
reconciliation for Bamboo Forest + Expert In Herbivores. The local export and
the same-generation prototype snapshot share the pair count (1,191) and their
unrounded point estimates match. This is a local producer self-check; a
production comparison still requires a same-version published reference.

## Phase 2 result

The representative same-generation local slice and the VM read-only serving
smoke test are complete. Cards and Card + Card producer outputs reconcile their
counts and unrounded values locally; Players history, MW point estimates, and
ordinary standalone EV CI have representative read paths and benchmark results.
The VM completed the current in-scope reads, including four consistent
concurrent readers. The first optimized full vertical-slice builder now
completes on the 4-GiB VM with two threads, a 2.8-GB DuckDB ceiling, and disk
spilling. The private run completed in 344.421 seconds without OOM; its build
and post-build read reports are `analysis/phase5-optimized-builder-benchmark.json`
and `analysis/phase5-postbuild-read-benchmark.json`. This validates the
memory-safe prototype path, but production daily-build orchestration and a
full end-to-end refresh still require Phase 5 integration.

Production serving is not switched by this prototype. Before any cutover, the
remaining work is the later Phase 3/4 implementation and reconciliation of the
serving API, atomic generation/rollback workflow, and the remaining page
families. The public default pack also remains on its existing older data
version; this prototype did not publish or deploy it.
